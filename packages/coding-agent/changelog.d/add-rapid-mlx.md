### Added

- Added implicit, keyless Rapid-MLX discovery at `http://localhost:8000/v1`, explicit `discovery.type: rapid-mlx` configuration, and served context-window metadata. Implicit and dedicated Rapid-MLX discovery requests to a loopback endpoint use a 500 ms timeout and a direct socket that does not follow redirects, so an unresponsive or redirecting server cannot stall startup or forward `RAPID_MLX_API_KEY`. A credentialed loopback probe goes over a direct socket by default, so `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` (including a proxy a project `.env` declared) never receives the bearer. The implicit probe only publishes entries that carry a Rapid-MLX-native field, so a vLLM-only server on port 8000 keeps its own `vllm` catalog, and that admission policy is part of the discovery cache provenance; an `offline` refresh republishes the cache only while the cached row was admitted under the current policy.
- By default, Rapid-MLX completions use the same direct loopback transport as discovery, so a configured `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` never receives the bearer or the request body. Keyless `/models` probes use it too, so a proxy cannot answer discovery and inject a catalog. Default non-loopback requests keep the normal proxy-aware transport, a caller-supplied `fetch` owns its transport and redirect policy, and the implicit vLLM/SGLang loopback probes skip individual entries that carry a Rapid-MLX-native field.
- By default, Rapid-MLX inference on the `openai-responses` api uses the same direct loopback transport, so that supported path cannot forward the bearer or the request body to a proxy either. A catalog cached by implicit loopback vLLM/SGLang discovery before the reciprocal identity guard is refused on an `offline` refresh instead of being republished.
