### Fixed

- A freshly created ACP session whose host accepts and starts the first turn before it has finished coming up, then fails it as `prompt_failed`, is retried a bounded number of times instead of ending the session on its first turn with an opaque `-32603` (issue #5574). The retry re-submits the first prompt as a new, independent `turn.prompt`, so it is gated to stay idempotent and correctly scoped: it fires only for a session's first logical prompt, only on a terminal the host classified as the startup-readiness class — a post-start `agent_failed` `prompt_failed` carrying a provider/transport classifier, never a provider rejection, an agent runtime failure or a deadline, however little output they produced — and never once the turn executed a tool or published assistant output — so a progressed, side-effecting turn is surfaced rather than re-run twice, and a re-submit can never stack a second answer on top of the failed attempt's text. A failed terminal that carries the whole answer as `finalText` with no preceding stream chunks counts as published output too, because that text reaches ACP consumers on an async tail after the attempt has already been rejected.
- `firstPromptDone` is preserved across endpoint reattachment (derived from the session's retained settled prompt correlations, and from a replayed prior user turn on load) so a prompt after a transport reconnect or `session/load` is never mistaken for a first prompt and given the retry path. A request rejected in preflight (empty/invalid prompt, auth/preflight failure, stale-state conflict, oversize frame, or provider bootstrap failure) no longer consumes the one-shot first-turn retry budget, so a later valid first prompt that hits the startup readiness race is still retried.
- The session is reserved for the duration of the retry's readiness backoff. After the failed attempt clears its active prompt, a concurrent ACP request can no longer slip into the backoff gap, steal the first turn, and force the authorized retry to fail with a conflict. A `session/cancel` arriving during that backoff is honored — the cancel intent is retained across the gap even when the adapter cancel is unacknowledged, and the retry re-checks it before resubmitting — and a `session/close` or `session/delete` that wins the gap now settles the parked retry with the teardown's own outcome, so a client-driven close or delete reports `stopReason: "cancelled"` instead of a `not_found` error raised against the record it just removed, or a `connection_closed` rejection that belongs to an involuntary transport loss. The retry also waits out the failed attempt's own final-text and failure-diagnostic publications before resubmitting, so a client slow to accept those updates can no longer make the authorized retry fail with a `conflict` raised by its own predecessor.
