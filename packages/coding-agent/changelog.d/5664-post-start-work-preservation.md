### Fixed

- A prompt that fails after execution started no longer strands the worktree edits it already made. The ACP settle path now snapshots uncommitted tracked and staged work into the git stash list — through a bounded capture local to that path, which never resets, cleans, or commits — before the turn reports `error`, and states the resulting stash ref in the failure payload so an operator can recover it with `git stash apply` once the worktree has been swept. The capture is budgeted end to end: each git child is spawned with the smaller of a per-command cap and whatever remains of a single whole-capture deadline, and a child with too little budget left is not started at all rather than being given an unbounded one, so a slow or hung git cannot delay the terminal outcome that settlement is about to report. Skipped or expired steps degrade the report — an observation that never ran is "could not verify", never "clean" — rather than changing the outcome. It counts untracked files rather than reading their contents. Untracked files are deliberately **not** claimed as recoverable from the stash ref: `git stash create` snapshots tracked content only, and the non-destructive alternative does not exist (`git stash push -u` mutates the worktree). They are instead reported as uncaptured, by count, so the operator knows to keep the worktree. A snapshot is only reported as complete when the capture is fenced against the snapshot it just took: `git diff --quiet <stash-oid>` confirms the working tree still holds exactly the tracked content that was captured, and a separate re-read confirms no untracked file appeared. The fence is content-aware, so it catches a tracked file edited while the snapshot was being written — a case a coarse dirty/clean re-check cannot see, because the file is dirty either side of the capture while the stash holds only the earlier bytes. A worktree that changed mid-capture, one whose fence reports divergence, and one whose fence could not be run at all all keep whatever stash ref was obtained but are reported as an incomplete snapshot, with wording telling the operator the worktree changed and must be kept. Preservation is scoped to the post-start phase rather than to one failure category, because any post-start fatal strands work.
- A worktree that could not be inspected is now reported as unverified rather than as clean. A missing workspace, a directory that is not a git repository, a git binary that fails or is killed by the capture budget previously produced the same "No uncommitted work was found to preserve." as a genuinely empty tree, so an operator whose dirty worktree simply could not be read was reassured and discarded it. Those cases now say the work could not be verified or preserved and that the worktree must be kept. A failure that never reached execution no longer asserts anything about the worktree at all: no capture is attempted for it, so the operator wording stays silent on the subject rather than reporting a check that never ran. Preservation remains best-effort and still never changes the terminal outcome the caller would otherwise have produced.
- A post-start failure classified `provider_transport` now says so in operator-facing wording instead of reading as a failure of the user's task. The reported `server_is_overloaded` case surfaced only as `Internal error: Provider failure after execution started.`, which names no cause an operator can act on. The new wording is assembled solely from the bounded safe classifier tokens — the category, a `providerCode` that passes `isSafePromptFailureCode`, and a hex stash oid — so no provider text reaches the wire. The JSON-RPC code, the `code`/`details` pair, and every `PROMPT_FAILURE_MESSAGE_*` constant are unchanged; the wording travels alongside them. Retry behaviour is unchanged: the post-start resume gates that refuse to re-run a turn which already executed a tool are untouched.
