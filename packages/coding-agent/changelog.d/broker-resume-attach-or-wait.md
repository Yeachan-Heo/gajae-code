### Fixed

- A broker `session.resume` (ACP `session/load`, Telegram `/session_resume`, `gjc sdk session raw global --op session.resume`, coordinators) of a session that another gjc process holds no longer launches a second session host over it. In the window where an interactive TUI holds the session but has not yet published its SDK endpoint (while it starts, or right after `/resume` switches to the session), the broker now waits up to 8 seconds (never longer than the request's readiness timeout) for that endpoint and reuses it, as it already did for a TUI whose endpoint was live. Before, it either refused (`endpoint_stale` for a TUI's startup row) or launched a host that became a second writer. If no endpoint appears, for example from a TUI started with `GJC_SDK_DISABLE=1`, resume fails with `live_session`, a message naming the holder (`another terminal (pid N)`), and a `holder` field with its surface and pid. A launched host whose own claim is refused under `session.ownership.mode: enforce` reports the same `live_session` outcome instead of `spawn_failed`. ACP adds `holder` to the error's `data` and no longer wraps this refusal as an MCP startup failure; `gjc sdk session` adds the `lifecycle_session_held` diagnostic; Telegram shows the message. A session nobody holds is launched as before, and `session.create` and `session.fork` are unchanged. This applies under the default `observe` too: a resume that used to give an embedding or the desktop app a second writer beside it now fails with `live_session` instead. The broker rereads `session.ownership.mode` for each resume, so `gjc config set session.ownership.mode off` restores the old behaviour at once. A retry once the holder is ready needs a new request key, because the broker replays a finished request's answer for the same key.
