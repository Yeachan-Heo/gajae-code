### Fixed

- A broker `session.resume` (ACP `session/load`, Telegram `/session_resume`, `gjc sdk session raw global --op session.resume`) of a session another gjc process holds now waits for that process's SDK endpoint instead of launching a second session host.
  - **When it applies:** an interactive TUI holds the session before its endpoint is published, while it starts and right after `/resume` switches to the session. Before, resume either refused (`endpoint_stale` for a TUI's startup row) or launched a host that became a second writer.
  - **How long:** at most 2 seconds under `observe` and 8 seconds under `session.ownership.mode: enforce` (the default), and never longer than the request's readiness timeout. The wait counts from when the broker received the request, so resumes queued on one session don't add their waits up. If the endpoint appears in time, resume reuses it, as it already did for a TUI whose endpoint was live.
  - **When no endpoint appears under `observe`:** resume never refuses and goes on as before ownership. Beside an embedding such as the desktop app, it launches a host, which counts the conflict. A TUI started with `GJC_SDK_DISABLE=1` gets the old `endpoint_stale` answer, with no launch.
  - **When no endpoint appears under `enforce`:** resume refuses with `live_session`, a message naming the holder (`another terminal (pid N)`), and a `holder` field with its surface and pid. A launched host whose own claim is refused reports the same `live_session` outcome instead of `spawn_failed`.
  - **Clients:** ACP adds `holder` to the error's `data` and no longer wraps this refusal as an MCP startup failure. `gjc sdk session` adds the `lifecycle_session_held` diagnostic when the broker names a holder. Telegram shows the message.
  - **Unchanged:** a session nobody holds is launched as before, and `session.create` and `session.fork` don't change.
  - **Changing the mode:** the broker rereads `session.ownership.mode` at the probe and at every poll, so `gjc config set session.ownership.mode off` (no wait) or `observe` (no refusal) reaches a running broker at once, even mid-wait. A raise reaches the broker only after a restart, but hosts it launches read the mode when they start.
  - **Retrying:** a retry once the holder is ready needs a new request key, because the broker replays a finished request's answer for the same key.
