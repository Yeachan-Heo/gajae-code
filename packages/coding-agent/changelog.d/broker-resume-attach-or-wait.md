### Fixed

- A broker `session.resume` (ACP `session/load`, Telegram `/session_resume`, `gjc sdk session raw global --op session.resume`, coordinators) of a session another gjc process holds now waits for that process's SDK endpoint instead of launching a second session host. This covers the window where an interactive TUI holds the session but has not yet published its endpoint: while it starts, or right after `/resume` switches to the session. The broker waits up to 8 seconds, never longer than the request's readiness timeout, and then reuses the endpoint, as it already did for a TUI whose endpoint was live. Before, it either refused (`endpoint_stale` for a TUI's startup row) or launched a host that became a second writer. If no endpoint appears, for example from a TUI started with `GJC_SDK_DISABLE=1` or from an embedding such as the desktop app, the default `observe` goes on as before ownership: it launches a host, which counts the conflict, and never refuses. Only `session.ownership.mode: enforce` refuses, with `live_session`, a message naming the holder (`another terminal (pid N)`), and a `holder` field with its surface and pid. Under `enforce`, a launched host whose own claim is refused reports the same `live_session` outcome instead of `spawn_failed`. ACP adds `holder` to the error's `data` and no longer wraps this refusal as an MCP startup failure; `gjc sdk session` adds the `lifecycle_session_held` diagnostic; Telegram shows the message. A session nobody holds is launched as before, and `session.create` and `session.fork` are unchanged. The broker rereads `session.ownership.mode` for each resume, so `gjc config set session.ownership.mode off` (no wait) or `observe` (no refusal) takes effect at once. A retry once the holder is ready needs a new request key, because the broker replays a finished request's answer for the same key.
