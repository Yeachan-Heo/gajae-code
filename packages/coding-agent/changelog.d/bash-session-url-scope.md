### Fixed

- Bash `rule://` expansion stays in the session directory, the repository root, the agent directory, a non-Git ancestor `.agent` or `.agents` rules directory under the trusted home (matched by physical path, so a symlinked home works), or a discovered user rule under `.agent/rules`, `.agents/rules`, or the agent directory. A `rule://` URL expands as its own shell word segment; a URL inside an argument the command already quotes, or a multi-line command, or a command that uses command substitution, backticks, heredocs, parameter or arithmetic expansion, or brackets, is refused instead of spliced into that context. A resolved rule path containing shell syntax is also refused. Bash no longer expands `memory://`: the memory store folds project paths such as `/work/acme-api/server` and `/work/acme/api-server` to one memory root, so the URL is rejected before resolution and stays on the internal reader.
- A Windows drive-qualified `rule://` path expands with forward-slash separators instead of being refused as shell syntax; a backslash that is not a separator, and a UNC path, is still refused.
- A `rule://` URL inside an `env` value expands even when the value is multiline: env values are data the shell never parses, so the command-text guards do not apply, while the same session and path authorization does.
