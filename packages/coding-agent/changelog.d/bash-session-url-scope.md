### Fixed

- Bash `rule://` expansion stays in the session directory, the repository root, the agent directory, a non-Git ancestor `.agent` or `.agents` rules directory under the trusted home (matched by physical path, so a symlinked home works), or a discovered user rule under `.agent/rules`, `.agents/rules`, or the agent directory. A `rule://` URL expands as its own shell word segment; a URL inside an argument the command already quotes, or a multi-line command, or a command that uses command substitution, backticks, heredocs, parameter or arithmetic expansion, or brackets, is refused instead of spliced into that context. A resolved rule path containing shell syntax is also refused. Bash no longer expands `memory://`: the memory store folds project paths such as `/work/acme-api/server` and `/work/acme/api-server` to one memory root, so the URL is rejected before resolution and stays on the internal reader.
- A Windows drive-qualified `rule://` path expands with forward-slash separators instead of being refused as shell syntax; a backslash that is not a separator, and a UNC path, is still refused. Like every other internal URL, the expanded path assumes the bash-compatible shell this tool starts: a non-POSIX shell configured by hand is outside that contract.
- A `rule://` URL inside an `env` value expands even when the value is multiline: the bash tool passes env values through as data and never parses them as command text, so the command-text guards do not apply, while the same session and path authorization does. A value keeps its own delimiters, and a path that would need the caller's format to escape it (a quote, a backslash, or a control character) is refused rather than spliced, because an env value's format is the caller's.
- `rule://` name lookup resolves against the requesting session's rules instead of the process-global snapshot the last top-level session installed, so two sessions with different rule sets cannot see or borrow each other's rules. A session with no rule list resolves no rule rather than falling back to that snapshot; the `read` tool's `rule://` route is unchanged.
- A `rule://` path carrying a glob, tilde, or whitespace character is refused when the command also invokes `eval`, `source`, or `.`, because that builtin's own parse removes the substituted quoting and can expand the path outside the authorized root. The same path still expands in a command parsed once, including a project directory whose name legally contains `[`, `{`, or `*`.
