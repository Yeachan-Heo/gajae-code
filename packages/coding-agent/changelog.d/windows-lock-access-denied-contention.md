### Fixed

- On Windows, concurrent `gjc` processes no longer fail each other's file-lock release and acquisition with `Failed to roll back file lock published during removal transition: owner_mismatch`. The native `access_denied` that NTFS reports while a peer holds a handle inside the lock directory is now treated like `sharing_violation` in file-lock and session-state-lock release, the publication rollback is retried briefly, and exhaustion names the real code. File-lock removal refusals reported to `removeFileLockDirForGc` callers now carry `access_denied` / `sharing_violation` instead of `EACCES`.
- Lock waiters open, read, and close `<lock>/info` in one synchronous step per poll instead of holding the handle across awaits, which previously blocked the owner's rename of the lock directory. On Windows, an owner record that is refused while another process is removing it (`EPERM`, `EACCES`, `EBUSY`, or `EBADF`) is treated as a changing lock: the waiter polls again, the timeout message says the record is being replaced, and a Windows `EBADF` from a lock identity capture is contention like the other transient codes. `gjc gc --disk` reports a lock tree whose removal Windows refuses as `withheld` rather than `entry_remove_failed: owner_mismatch`. Behavior on other platforms is unchanged.
