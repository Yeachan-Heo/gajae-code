### Fixed

- A managed fallback chain no longer abandons a healthy model when its account is merely running its maximum number of parallel requests. A 429 with a typed concurrency code (`session_limit_reached`, `concurrency_limit_exceeded`, `concurrent_request_limit_exceeded`, `too_many_concurrent_requests`) used to be treated as an ordinary rate limit: a few seconds of retries spent the entry's attempts, marked the credential, opened the selector circuit for sibling sessions and advanced to the next model. The session now waits on the same entry without spending attempts, marking the credential or opening the circuit. When no provider Retry-After is present, it polls between 100ms and 15 seconds with random jitter; when Retry-After is supplied, the wait respects that deadline plus bounded jitter (0–1s when Retry-After > 0) to desynchronize concurrent waiters. The wait is bounded per request by the new `fallback.concurrencyWaitMs` setting (default 5 minutes).
