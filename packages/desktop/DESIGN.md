# Gajae Code Desktop

## Brand

The app icon, the sidebar badge and the empty state use the Gajae-Code character that the repository already ships in `assets/character.png`: a warm dark rounded tile with the straw-hat mascot and its visor. `packages/desktop/icon.png` is the tracked 1024 px app-icon source: its artwork occupies a centered 824 px square with 100 px transparent margins on every side, matching the optical bounds measured in installed macOS app icons. Preserve that padding when replacing the artwork; a full-bleed tile looks oversized in the Dock and Finder. The tile has a smooth 184 px corner radius, with the illustration clipped to its silhouette. Artwork must not protrude below the rounded corners: native macOS icon rendering otherwise shrinks it onto an unwanted white fallback plate. `bun run icons` regenerates `src-tauri/icons/` (gitignored) from it; the Tauri bundle explicitly includes those icons, including `icon.icns` for macOS. `src/assets/gajae-mark.png` remains the separate, unpadded 256 px tile the renderer shows at 26 px in the sidebar and 88 px in the empty state. Brand art is raster and local: the renderer never fetches a remote image.

## Workflow: EXISTING DESIGN SYSTEM

Extend the existing warm-neutral desktop system, component library and `?showcase` harness. This is not a greenfield redesign. Preserve project organization, parallel conversations, long-running work and reviewable outputs in a first-party GJC interface. Codex-style means compact navigation and a quiet reading/composing workspace, not copied branding, vendor assets or product claims. Historical reference: https://developers.openai.com/codex/app/ (retrieved 2026-10-27; redirected to https://learn.chatgpt.com/docs/app); no third-party material is vendored.

## Layout

Muted 264px left sidebar groups conversations by project, displaying Working/Done/Needs input/Error independently of selection. Its bottom-right toggle switches to a persistent 64px navigation rail: project buttons show the first two Unicode characters, conversation buttons show only status indicators with full accessible names and hover titles, and settings/open-project remain icon actions. Below 760px the sidebar collapses to that rail automatically instead of hiding behind a drawer; its toggle still expands the full sidebar in place. That expansion lasts until the window narrows again and never rewrites the saved preference, which applies again once the window is wide enough. Each workspace lists five conversations and appends up to five more per `Show more` click; the compact rail uses an ellipsis button for the same pagination. A selected conversation beyond the page keeps its row visible. The page limit lives in the renderer and never changes stored data. Compact toolbar names the selected project/session. Its icon-only `Session status` button (gauge, between Activity and the conversation actions menu) opens `.session-hud-panel`: one `.session-hud-tile` per TUI status-line field — model, reasoning, context %, cost, branch, PR, jobs, speed, title, directory and gjc version — each an icon plus a short label, with `—` (accessible name `Unknown`) for anything the host did not report rather than a fabricated zero. Branch, jobs, speed and version come from `session.info`'s `hud`; the PR comes from a separate `session.pullRequest` read (`gh pr view`) that runs once per branch, shows `…` while it is in flight and opens only a validated GitHub URL. The panel re-reads on every status/message/model change of its conversation and every 2s while a turn runs; a read requested while one is in flight runs once that one lands, and a failed read keeps the last values beside the error. The full usage report stays one `Details` disclosure below the tiles. Central conversation reading column and sticky bottom composer. Optional right changed-files/diff pane. Settings and command navigation require no terminal. Empty states offer a single primary action; the zero-model `.provider-notice` docked below the conversation-selection empty state is a separate notice, not a second empty-state action.

### Session work panel

Use the existing design system for a compact, rounded `Session work` card anchored below the toolbar at the upper right, visually related to the composer rather than a full-height sidebar or drawer. The user's two reference screenshots establish the upper-right toggle and content-sized card; unlike their overlay, our layout reserves a right-hand column while open so conversation text and composer never overlap the card. The card has a bounded scrollable body but does not stretch to viewport height. On narrow windows place the same nonmodal card in normal flow above the conversation, with a smaller height cap; never use a backdrop or side sheet. Review and Session work share one card slot and one per-session selection: closed, Review, or Session work. Choosing either card replaces the previous selection rather than hiding it; toggling the active card off or pressing Escape leaves the slot closed and never restores the previous card. An untouched session may automatically show work when content arrives, but an explicit closed selection stays closed through updates. Both cards share the same compact surface, header, height cap and reserved right-hand space. Review remains explicitly toggled, retains file selection and a scrollable diff, and uses the same nonmodal above-conversation placement on narrow windows; neither surface becomes a full-height sidebar or drawer. The toolbar icon retains its accessible name, tooltip, expanded state and pending-input badge. While the session has tasks, a compact `done/total` `.session-work-progress` chip follows the icon (muted, `--status-done` once every task is finished, and the body ink while the card is open, since accent or green text on the pressed accent tint falls under 4.5:1 in some palettes) and the button's name and tooltip carry the same progress, e.g. `Session work, 2 of 5 tasks done`; the chip itself is `aria-hidden`. Content automatically reveals the card unless the user explicitly collapsed it for that session; manual open/close wins over subsequent updates and session switches restore each session's choice. Open cards give their toolbar toggle an accent-tinted background and border plus pressed/expanded semantics; the header has no duplicate close button. Clicking the toggle again or pressing Escape closes the card and restores focus to its toggle. Nested details and gate dialogs retain their own native presentation lifecycle.

The panel groups TODO, actionable Goal, background jobs, subagent tasks, schedules, workflow summaries and pending question/approval requests using the existing SDK projections and controls. Input requests are inbound questions/approvals, not queued outgoing messages. Outgoing message queues, recovery notices and immediate question cards remain above the composer; no repeated TODO/Goal block remains there. The task list lives only in this card; the toolbar chip is its always-visible signal, standing in for the terminal's persistent list. Empty groups and zero-count prose are omitted; an entirely empty session does not automatically open the card. Explicitly opening an empty card shows only one compact empty-state line. Actual errors and unavailable observations remain distinguishable from empty data. Failure acknowledgement carries the single-use token from the displayed SDK snapshot; background reads never substitute a newer snapshot's authority. Display fields mask complete credentials before limits and remask after normalization, including task/goal text and streamed terminal output. There is no refresh button: initial/reconnect reads and the existing host activity subscription keep state current even while collapsed. No backend capability is implied by this layout change. The composed Session work showcase covers empty, populated, pending, error and unavailable states.

Session status has no refresh button: while open and connected, read once per second including idle sessions, coalesce slow reads and fence closed/replaced dialog responses. Metadata, live run/tool/usage state and the HUD's branch, owner-scoped jobs, output rate and engine version map directly from public `SdkComposerObservation.info`, not reconstructed internal telemetry. The public DTO does not expose a session-file path, so its display field stays null; it is never a guessed native file selector. The existing pull-request link uses a read-only app-local Git/gh query with a bounded per-repository/branch cache because the public SDK has no pull-request DTO. MCP rows retain actual configured display names through public SDK labels, sanitized/redacted before display; opaque SDK refs, never names, own actions. These backend mappings do not change the latest screen layout or controls. The desktop composer handles `/clear` as new-conversation creation in the same project, not SDK history clearing. Keep the old conversation and refuse attached files or arguments without consuming the draft.

## Tokens

System sans-serif, 14px (0.875rem) base, line-height 1.55; medium-weight compact headings and 12px secondary metadata. Use rem typography so browser text scaling remains effective. Icons beside text that grows with the text size are sized in rem too: tool rows and tool-call cards, the dialog close button (a 2.125rem box), the Providers Back chevron and the conversation toolbar's buttons, all 16px (and a 34px close button) at the default size. Monospace is reserved for paths, code and tool output. Assistant prose and display reasoning use semantic safe Markdown; user text and tool output keep their original whitespace.

Shape, elevation and motion come from one soft, rounded scale rather than per-component numbers: `--radius-xs` 8px, `--radius-sm` 10px for controls and session rows, `--radius-md` 13px for tabs and nested cards, `--radius-lg` 16px for panels, user messages, question cards and the composer, `--radius-xl` 20px for the modal, `--radius-pill` for chips. `--border-soft` (a 58% tint of the theme border) draws structural edges, `--surface-2` fills inset surfaces, `--shadow-rest`/`--shadow-soft` give controls and overlays a shallow lift, and `--ease`/`--dur` keep transitions at 160ms. Inputs and buttons share the same 10px radius; a focused field swaps its border for the accent and an `--ring` halo instead of an outline. Both dialog tab bars (model picker and settings) share one surface-and-pill pattern with the same raised selected state; the model bar stretches its two tabs to the full width, while the settings bar sizes four tabs to their content and wraps at narrow widths.

Palettes come from the bundled TUI themes (`packages/coding-agent/src/modes/theme/defaults`): red-claw (default), blue-crab, claude-code, codex, gruvbox-dark, opencode and ouroboros. `themes.ts` owns the runtime source: `applyTheme()` writes the selected palette to the document as custom properties before first paint. CSS keeps one static red-claw fallback block so the app is never unstyled before that script runs; that fallback must be kept in sync with `themes.ts` whenever the default palette changes. Every bundled theme is a dark palette, so the desktop follows the selected theme instead of the operating-system color scheme, and `color-scheme: dark` keeps native widgets consistent. Accent hover, accent tints and error tints derive from `color-mix` rather than hand-tuned duplicates. The shared `.error-banner` writes its message in the theme's `--error` mixed 72% toward `--text` on its `--error-soft` tint (its icon and edge keep the pure hue), which clears 4.5:1 in every bundled palette. A `.button.danger` (Delete conversation, Stop and disconnect, a job's Stop/Cancel/Delete) writes its label in the fixed `--status-error` mixed 72% toward `--text`, which clears 4.5:1 on a card or dialog and on the hovered and pressed surfaces in every bundled palette, and carries a solid `--status-error` edge: a red-orange accent (Red Claw, Claude Code, Gruvbox Dark) sits within about 30° of that red, so danger never rests on hue alone, and plain and primary buttons have no such edge. Theme choice is a browser-local display preference stored under `gjc.desktop.theme`; it never writes shared terminal configuration, and unknown or blocked storage falls back to red-claw.

Execution status uses four fixed hues that stay distinguishable on every palette: Working blue `--status-running`, Done green `--status-done`, Needs input amber `--status-waiting`, Error red `--status-error`; Idle stays muted. These are deliberately independent of `--accent`, because the default red-claw accent is already orange-red and would erase the difference between a running turn, a question and a failure. Sidebar status rows pair hue with icon and text; the conversation header repeats the same words without the icon, so header and sidebar always agree: a conversation whose turn finished while the app was running reads Done, and one merely opened with history from an earlier run reads Idle.

### Component anatomy and slots

- `.message` retains role, truncation notice and actual ordered text/thinking/image content. Either requests the full redacted message by entry ID and session generation through `message.copyText`, never copies a bounded preview, and excludes thinking, images, tool calls/results and partial/error output; image-only prompts have no copy action. Provider-limited final text remains copyable. Unknown managed-owner terminal metadata does not authorize a copy action. The complete success envelope is bounded at 8 MiB with an explicit failure rather than silent truncation. ## Ownership

The app's catalog and logs live under its desktop data root. New app conversations use the shared SDK-managed session store; existing private catalog transcripts remain under their desktop data root. Public SDK embedding operations own creation, opening, forking and identity-verified deletion in either store; discovery alone never grants a writer lease. When fork publication rolls back, only its caller owns the catalog compensation write; that exact rolled-back owner cannot issue another save during teardown or retained cleanup retries. Normal workspace teardown still persists its final settled view, including an explicit root selection, after removing the live map entry. A lightweight publication token fences that save across asynchronous flushes and successor ownership. If SDK work has settled while the host still awaits a terminal delivery receipt, teardown transfers exact-view persistence before disposing the SDK; the receipt remains pending and the exclusive request joins that same persistence outcome before responding. Pending questions and per-owner cancellation use that exact live publication's token, not its reusable catalog session ID, so a late retiring request cannot answer a successor's question; intentional host-wide shutdown still cancels every pending question. Failed durable compensation retains every transcript identity still referenced by the last saved catalog. Agent configuration, credentials, model profiles and the default preset share the terminal installation by default; `GJC_DESKTOP_ISOLATED=1` gives tests/QA an isolated install. Initial target macOS 15+ arm64 (WebView must support Promise.withResolvers). Closing last window hides app while tasks continue; explicit Quit cancels/disposes owned work. #7322 owns upstream parity; consume public SDK, never private endpoints or terminal controllers. Expose unavailable capabilities truthfully pending upstream implementation.

A conversation the app created can be released without deleting it. `session.disconnect` saves its final view, disposes the live session and keeps the catalog row with a persisted `disconnected` flag, so the terminal can continue the same transcript; work in progress is stopped only after explicit confirmation, through the same path as Stop. A Disconnect fences the conversation before its first wait: every request that arrives after it is refused (an input's draft comes back) until it finishes, and one that only asks for confirmation lifts the fence again. Once it commits, it counts as a Stop for every input that arrived before it. Its waits are bounded: if the run, a stopped `!` command or the final view has not settled within 5 seconds, it fails with "The conversation is still stopping. Try Disconnect again.", lifts the fence and releases nothing; it then waits up to 5 more seconds for inputs still being admitted and for the receipts of inputs it stopped, so it normally answers with every such receipt final, but a receipt still being written past that wait (an input hook that runs longer, say) becomes final afterwards, with the same disposition. A waiting approval counts as work that needs confirmation, and Disconnect never answers it. Deleting a released conversation, or an idle one the app holds open, needs a definite answer from the broker (nobody has it open, or no broker runs); a broker that runs but cannot answer refuses the delete. Until `session.connect`, its history is read from the transcript (`readEmbeddedTranscriptHistory`), reads never open a writer and every writing request refuses before work starts. Connect reopens through the normal path, which lands on a tail another surface appended. Every saved view records the transcript tail the app held when it was saved; an open restores the view only while that tail is still the newest entry, and otherwise lands on the newest entry, so another surface's turns are visible and the next prompt continues them. A row saved before tails were recorded has no such evidence: its view is restored unless its position is a strict ancestor of the newest entry (`isEmbeddedAncestor`; the empty root counts as an ancestor of every entry), because a strict ancestor was the end of the transcript when the view was saved and what follows it was appended later. A position on another branch was a deliberate choice and is restored. Before the app opens its own writer for an existing transcript (first open, Connect, a stale-copy reload), before every write it starts in an idle conversation (prompt, `command.run`, retry, compact, rename, revision, model or reasoning change, `!` command, goal, preferences, tools and MCP operations, an activity operation that resumes work, delete; stopping, cancelling, pausing or deleting background work never waits on the broker) and when an idle conversation it holds open is selected, it asks the running broker whether another live process holds that transcript open (`findEmbeddedLiveOwner`, at most 500 ms); if one does, the conversation is `elsewhere`: read-only like a disconnected one, delete refused, and select or `Check again` checks again, telling the user when the other process still has it. The check never starts a broker; with none running, or one that fails or is slow, the app opens or writes as before and compare-and-append remains the backstop. A turn that started while a check was waiting is never released under it; the next write checks again. An answer that arrives after another request replaced the copy that asked applies to the copy that replaced it, once. Stepping aside is registered like a reopen, so a request that arrives while the copy is released joins it and answers as it does. Stepping aside and a stale-copy reload never end background work the session owns (running jobs and live tasks, read from the SDK's job view; schedules are not counted, because the SDK keys them by an agent id every app conversation shares): while it runs and a terminal has the transcript, select keeps the app's copy and every other checked request is refused before it starts; Disconnect asks first, reports how much, and ends it with the session. Connect while a terminal still has the transcript keeps the persisted `disconnected` flag until an open actually holds the writer again, so a restart before then finds it released. What the check cannot cover: (a) a terminal that opens the transcript after a check, until the last write of the turn that check let through (steers, follow-ups, goal continuation and the auto-title belong to that turn); (b) a turn the SDK starts by itself when owned background work completes: no Host request precedes it, so nothing checks before it writes; (c) no broker running, or one that does not answer within 500 ms. In each case the managed store's compare-and-append refuses whichever writer appends from an older position, the terminal included, so the transcript never branches: the refused side's write does not land, and the app hands a refused prompt back and reloads. The session DTO's structured `connection.state` (`connected`, `disconnected`, `elsewhere`) drives every read-only surface; rows another surface owns through the SDK carry none.

Project registration and re-opening refresh the read-only SDK inventory for that exact canonical project/header cwd, including existing terminal conversations. Bootstrap (at startup and on window focus) answers with the current catalog at once and re-lists open workspaces in the background, one pass at a time with focus bursts folded into one more; a pass that finds something emits a snapshot, followed by the full rows of every open conversation so the refresh never shrinks the transcript being read. The desktop catalog retains identity and creation metadata, never a copied transcript or a shared-file writer lease. Snapshots use original creation chronology across desktop sessions and late imports; registration time never makes an older conversation newest. Selecting a managed reference uses public SDK lifecycle admission and an incarnation-bound Router attachment. It never opens that transcript through a local desktop controller or takes over/stops the terminal owner. Closing the workspace/app detaches these remote clients only. Mutations carry the rendered session generation and remain pinned to the validated attachment; retired controls cannot target a replacement owner.

Managed conversations support history, textual prompt/steer/follow-up, client-owned abort and owner model/thinking controls. Unmapped operations fail explicitly instead of falling through to desktop-local writes. Remote question/approval presentation and answers remain unavailable because their SDK lane does not provide the desktop's presentation/retirement contract; pending gates stay waiting and direct the user to the original control surface. Remote images, presets/default-role settings and other unmapped panels are likewise unavailable. A preferences-read failure must not discard a valid remote model catalog or prevent a session-only model selection. Lost acknowledgements never trigger input replay; prompt/steer use SDK clientRef reconciliation, while an unacknowledged follow-up remains unknown because the SDK does not retain its clientRef.

The release app bundles both the compiled SDK host and the real `gjc` CLI beside its native executable. Native startup prepends that private executable directory to the host's PATH, so workflow commands and task subprocesses require no separate global `gjc` or Bun installation. SDK-owned `process.execPath sdk …` child modes enter the real CLI before desktop environment setup, preserving SDK admission and ownership. Only a primary pointer that starts and ends outside the modal closes it; either cross-boundary drag preserves it. Delete confirmation separates the question from an explicit irreversible warning using the danger color and an icon. Suppress the browser context menu inside the app without blocking normal typing, paste or keyboard selection. Controls share compact boundaries, heights and radii; routine running status says only `Working`. Keep actionable recovery and error feedback, not repeated helper prose.

### Workspace layout and session-state panels

Workspaces retain explicit host-catalog order: workspace heading pointer-drag and the menu's `Move workspace up`/`Move workspace down` call `project.reorder`, preserving closed workspace slots. Pressing a heading/name (including compact initials) and moving beyond the drag threshold enters a move state; the pointer's position chooses a before/after boundary, rendered as a clear accent insertion line across the target group. Release dispatches exactly that permutation. A simple click still collapses/expands, and the new-conversation button is not a drag handle. Escape, pointer cancellation, connection loss and unmount clear the gesture without sending. The host snapshot remains authoritative: no invented successful optimistic order. Both expanded sidebar and compact rail use this interaction; conversation rows remain non-draggable. Conversations display the host catalog's append sequence in reverse, newest-created first, before pagination. A status or message update replaces a session in place and does not shuffle the list; an appended new session appears first. The renderer never mutates the source array. Manual conversation move items are removed because they conflict with newest-first display. Workspace reordering and conversation context-menu selection remain available in the compact rail.

Right-clicking a workspace, or pressing ContextMenu/Shift+F10 on its heading or a conversation, opens `.context-menu` over a dismissing `.menu-scrim`; the menu takes focus, Escape closes it before the review pane, it is clamped inside the window, and move items are disabled at the ends of the list. A conversation's menu offers `Open conversation` and `Rename`; the rename dialog is bound to that conversation rather than the selection, so any listed conversation can be renamed without opening it, and it closes if the conversation leaves the snapshot. The conversation actions menu gives every item a decorative icon and carries retry, export, active-tools and goal management alongside its existing conversation operations, but no rename, full-history or run-settings entries. Slash commands are discovered through the composer's `/` recommendations and submitted from the composer; there is no separate Commands button or command dialog. `Close workspace` sends `project.close`, which marks the catalog entry `closed`: the workspace and its conversations leave the snapshot, its live session is retired, and the directory, session files and metadata are never deleted. The closed flag is persisted, so it survives a restart; a closed workspace's conversations are not addressable until it reopens. `project.open` on the same path clears the flag and restores the same project identity, so reopening a closed workspace brings its conversations back instead of orphaning them under a new id. Open and close for one path are serialized: a reopen issued while a close is still retiring conversations waits for that teardown instead of observing a half-closed workspace, and the durable close publishes before the teardown so the workspace leaves the list immediately.

Builtin tools that own durable session state project it, rather than leaving it inside a tool result. `todo_write` becomes `DesktopSession.todos` (`getTodoPhases()`, capped at 24 phases/120 tasks/300 characters per item, so a pathological list is bounded rather than complete) rendered inside Session work as `.todo-panel`: collapsed it states `done/total tasks done`, the task in flight and a thin `aria-hidden` `.todo-progress` bar; expanded it lists phases numbered by position (a CSS counter, so the heading text stays the phase name) with their own done/total, and tasks with spoken status icons, a `.todo-note-count` badge and, for the task in flight only, its notes inline with their line breaks kept. Completed and abandoned tasks both count as done, as in the terminal. Each task carries at most its newest five notes, each redacted whole before the 300-character cut, so a full set reads `5+`; a list at the 120-task bound says only the first 120 are shown. When the newest settled `todo_write` row in the visible transcript failed (cancelled and in-flight rows are skipped), the group says the task list may be out of date; the renderer derives this from messages. An expanded `todo_write` row renders the same read-only tree from `tool.detail`'s `todo` and falls back to the row's own output without it or when the call failed or was cancelled. Review the states at `#showcase-todo-panel`, `#showcase-todo-card`, `#showcase-todo-chip` and `#showcase-todo-tool`. The `goal` tool becomes `DesktopSession.goal` (`getGoalModeState()`) rendered as `.goal-strip` with the objective, its status and only the operations that status allows (pause/complete/drop while active, resume/drop while paused, drop when finished). A goal with an unrecognised status or an empty objective is omitted rather than defaulted, and each usage number is dropped on its own when it is absent or negative; the strip's actions are disabled while a turn owns the session and its refusal is shown beside it; the Manage goal dialog applies the same state rule, and the conversation actions menu disables that action while a turn or a waiting session owns the conversation. Both panels render only inside the Session work card, never above the composer, are omitted entirely when the session has no todos or goal, and never invent state the SDK did not report. The desktop session is built from the full builtin registry with no reduced tool list, so `tools.list` reports every tool the SDK exposes and `tools.set` validates a selection against that same registry; each tool still applies its own settings and platform guard (a disabled renderer or a missing `gh` keeps its tool inert), and interactive tools keep their existing surfaces (`ask` kinds in `QuestionCard`, `resolve`/approval in `GateDialog`, MCP in `McpPanel`).

Session names come from the SDK's first-accepted-input automatic-title operation. `New session` is a catalog display placeholder, never a user-sourced transcript title. Manual renames win, retired owners cannot apply late generation, and a committed SDK title remains authoritative if its redundant catalog cache write fails; reopening reconciles that cache. Title work never changes delivery disposition.

## Native boundary

Rust is limited to `packages/desktop/src-tauri`: Tauri window integration, sidecar process lifecycle, and validated IPC transport. SDK behavior and application business logic remain in TypeScript. The repository Rust scope guard checks the `gjc-desktop` package identity and rejects Rust outside this native directory, including sibling desktop application code.

## Account authorization

The app uses public SDK authorization controls with a single app-owned authorization flow; the SDK retains credential and login-callback ownership. The Providers dialog is the only enrollment surface: per provider a sign-in method with an explicit HTTPS-only system-browser action, a device code (`verificationCode`, shown as its own block while `instructions` keeps the prose), optional code prompts and cancellation, and an API-key method. A provider risk warning is an acknowledgement, not a prompt: it shows the provider's notice verbatim in a `--status-waiting` tinted group whose heading takes focus (never the confirm button), appears only while the flow waits on it and before any authorization URL exists, is confirmed with the literal answer `confirm` and is declined through the same cancel action as the rest of the flow. On open the dialog reads `auth.state` once: an active flow is resumed in its provider's detail, while a terminal state from before the dialog opened is history and is not shown, so only a flow this mounted dialog started or resumed reports success or failure. Closing the dialog never cancels a flow; reopening resumes it. `Saved, but the model list could not refresh` comes only from the Host's explicit `catalogRefreshed: false`, never from the SDK's `stored` flag, which also reports credentials that existed before the flow; provider rows take stored-credential presence from `auth.providers` as current state, not as a flow outcome. Credentials are shared with the terminal app on the same machine. Disconnecting a provider and registering custom OpenAI-compatible endpoints are not available through the public SDK, so they are visibly unavailable: a disabled Disconnect with its reason, the list footer and two Capabilities entries. Prompt answers and keys are never persisted in frontend storage. Cancellation does not undo credentials a provider already saved; an uncooperative provider may require Quit and relaunch before another login. This is not proof of a completed real-provider login.

Before the SDK captures environment state, the sidecar strips inherited provider keys/tokens, routing/proxy overrides and CLI broker state. Shared mode restores the installation's HOME and resolved agent directory (including explicit agent-directory overrides); credentials remain in the SDK's shared storage, not a new Keychain implementation. `GJC_DESKTOP_ISOLATED=1` instead places HOME, agent, configuration and XDG roots under the app data directory for tests/QA. Neither mode is an execution sandbox for SDK tools.

## Delivery recovery and process ownership

Before clearing the composer, atomically retain its original text and ready attachment payloads in local IndexedDB. The host retains metadata-only delivery receipts and acknowledgment tombstones. Shutdown owns journal admission before dispatch and joins queued terminal receipt writes after SDK disposal; journal or publication errors never bypass workspace owner teardown. Catalog write failures remain part of shutdown's reported outcome even after a later successful compensation or teardown write; reporting a failure never skips SDK resource cleanup. Broken output channels and fatal input frames retire request admission rather than leaving invisible work running. Durable handoff and SDK preflight acceptance are not proof that a model run executed. Definitive refusal is distinct from provider failure, cancellation, and an unknown outcome; a disconnect or restart must never automatically replay potentially executed input.

Normal pending, accepted and queued delivery receipts remain durable internal bookkeeping, not recovery warnings; reconcile bootstrap receipts before exposing an unmatched record as unknown. Successful completion/cancellation and automatic definitive-refusal restoration do not flash alarming cards. Actionable unknown outcomes explain possible prior execution; failed outcomes use distinct copy without promising that execution never started. Known-unsent storage repair remains separate from acknowledgment failure. Unknown/failed recovery requires an explicit user action; definitive refusal/removal restores safely without replay. Stop ends the run and leaves the conversation idle; it never resumes into queued work, and an agent follow-up stays queued for the next turn. A stopped prompt, or an input its run took, is `cancelled` only with transcript evidence: the SDK bound that input's own user turn to a session entry the transcript still holds. Queued inputs are matched to turns by exact text, one turn per input: as each input settles it claims the first turn with its text that no other input, and no prompt's own scope-bound turn, has claimed. The SDK settles inputs in the order it took them and appends them in that order, and the only one taken but never appended is the steer a Stop hands back at the moment it is taken, so an identical earlier message cannot vouch for one that never ran. An input Stop kept from running is `removed` and restored; one the run took but never appended is `unknown`, even when the run itself completed. A prompt or steer that Stop catches before its run starts or it is queued (during its journal write, an input hook or the SDK's admission) is `refused`, which restores it, and starts nothing; Stops and inputs are ordered by when they reach the Host, so a Stop that settled before a message was sent never refuses it, and only a Stop that goes on to stop the run counts: one that only cancels a running shell command, or is refused, affects no input. Host-initiated aborts (workspace close, session switch) stay `unknown`. Restore preserves newer draft text and attachments; acknowledging the recovery record does not erase the restored draft. Several texts handed back at once (Stop returns every queued message) read in the order they were sent, above the newer text, whichever receipt arrives first and across a reload; records keep a per-device submission sequence because the store lists them by id. A restored text the user has since edited is never matched or replaced, only placed above. Network acknowledgment is bounded and does not hold the local draft-write queue. Repair and disposal controls belong to an exact delivery ID, not every delivery in the same session; unresolved known-unsent repair cannot be discarded. Each delivery is one `RecoveryCard` (`.recovery-card`): a bounded `--card` card at `--radius-lg` in the conversation's 800px reading column with the column's 16px gutter, so stacked cards stay apart. It reads top to bottom: what happened (the only live region), which conversation (`.recovery-conversation`: a bold `Conversation: {title}` line), an orphan's text, then one `.recovery-card-actions` row — `Retry recovery`, `Open conversation`, `Restore draft` or `Copy text`, and the discard action last. Inside the card an enabled action is filled (`--surface-2`) in the body ink and a disabled one is unfilled with a dashed `--muted` edge, not faded as well (fading hid the edge), so they differ by more than color; while a listed conversation's unknown outcome waits for its restore, a line under the actions says why Discard is unavailable and describes it. From the empty screen a listed conversation offers `Open conversation`, under its own open conversation it does not. A record whose conversation is not in the snapshot (deleted, or its workspace closed; the copy never claims which) is an orphan: it names the title remembered at send time, hides `Restore draft`, offers `Copy text` and may be discarded directly (`Discard record`), including an unknown outcome; its notice never mentions restoring, which it cannot offer. Because its text may be the last copy, an orphan card shows it in an inset `.recovery-text` block (bounded at 12rem and scrollable, whitespace kept, selectable, and a Tab stop only while it actually scrolls; behind a `Show the unsent text` disclosure past four lines or 280 characters); `Copy text` confirms visibly (`Text copied.` with a green check), a refused write shows an error-ink alert that tells the user to select the text and opens the block, and nothing is ever discarded automatically. Only the card's message is its live region, never the text or the copy feedback. A listed conversation keeps the rule that an unknown outcome is restored before it can be discarded. Deleting a conversation removes its Host receipts and its local records, so deletion never leaves orphans behind; when any of them holds text that is neither in the transcript nor back in the composer (an unknown or failed outcome, an input in flight or awaiting repair, a refused or handed-back input whose automatic restore failed; `recoveriesDroppedWithConversation` gives both that list and the records the deletion drops, so they cannot drift), the Delete confirmation says how many unsent messages it discards and offers their text with `Copy text` and the same visible feedback. Several messages stay separate: each is its own numbered (`Message 2 of 3`), selectable `.recovery-text` item in one scrolling list, and `Copy all text` puts a `--- Message 2 of 3 ---` line before each, so a paragraph break inside a message cannot be mistaken for a boundary. The dialog pins its question, warning and Delete; that list is its only scroller and gives up height first (as in the Tools and Providers dialogs), with the dialog's content as the fallback scroller.

The process entrypoint registers host teardown and final frame draining with the shared signal-exit owner. It does not race an independent LSP exit handler or remove unrelated signal listeners. Protocol-requested shutdown is a normal zero exit; SIGTERM retains the shared conventional status. Signal cleanup remains bounded by the existing postmortem deadline (5 seconds by default, configurable with `GJC_CLEANUP_DEADLINE_MS`); expiry can interrupt teardown or final frame flushing, so it is not a guaranteed-delivery contract. Unproven deliveries remain recoverable as unknown. QA fixtures use the same process lifecycle and observe real MCP transport termination and LSP process exit rather than inferring teardown from a stale-session error.
