# Architecture

## Runtime layout

The Bun workspace is divided into small packages:

| Package | Responsibility |
|---|---|
| `@gajae-gateway/protocol` | Versioned NDJSON frames, negotiation, verb/event catalogues, and canonical origins. |
| `@gajae-gateway/sdk` | Client for the gateway’s Unix-domain socket or stdio transport. |
| `@gajae-gateway/gateway` | Daemon: configuration, SQLite state, sessions, delivery, memory, monitors, and the `gjc` boundary. |
| `@gajae-gateway/adapter-discord` | Discord ingress and outbound delivery, including typing hints and the reaction-gradient presence. |
| `@gajae-gateway/adapter-telegram` | Telegram ingress and outbound delivery. |
| `@gajae-gateway/adapter-slack` | Slack ingress over Socket Mode, mrkdwn delivery, reactions, working-status presence, and missed-message recovery. |
| `@gajae-gateway/cli` | Owner commands over the gateway socket. |

## Authority Map

### Resource owners

| Resource | Owner | Boundary |
|---|---|---|
| Gateway process and gateway database | Gateway daemon, holding the `gateway` lease | The daemon acquires `gateway` then `memory` before opening its runtime; the service manager starts and stops it. |
| Memory corpus | Gateway memory writer, holding the `memory` lease | The lease serializes the Git-backed `$GAJAEWAY_HOME/memory` corpus with offline memory administration. |
| Broker process and agent state | `gajaeway-broker` service, holding the `broker` lease | The broker host runs the pinned GJC executable against `homeLayout(home).brokerAgentDir` (`$GAJAEWAY_HOME/broker/agent`). |
| Discord adapter | Discord adapter process, holding `adapter-discord` | Owns its adapter process for this home; it connects to the gateway as a client. |
| Slack adapter | Slack adapter process, holding `adapter-slack` | Owns its adapter process for this home; it connects to the gateway as a client. |
| Telegram adapter | Telegram adapter process, holding `adapter-telegram` | Owns its adapter process for this home; it connects to the gateway as a client. |
| Update and restart supervisor | CLI update/restart operation, holding `update` | Serializes binary installation and the ordered service restart; adapters and admin are clients, not database owners. |

Gajaeway provisions the private broker directory from an explicit file allowlist. The source `~/.gjc/agent` is read for that snapshot and drift checks; gajaeway does not write to that source. GJC itself is only invoked against the private broker directory.

### Active broker authority

SQLite records one active private broker authority and immutable gateway-created session bindings. A session ID alone is not ownership: controls require positive creation and binding evidence under that authority. A populated database with missing or mismatched authority fails before schema migration; only offline census and explicit cutover may change it. Cutover preserves historical records and quarantines accepted or unproven work rather than replaying it under the new authority. See the operator runbook for the backup, census, and export boundary.

### Transaction boundary

`StoreCore` owns the SQLite connection, schema migrations, and synchronous transaction boundary. `Store` composes the owner-group repositories. Each group receives a `GroupDb` from `StoreCore.groupDb(group)`: SQL is classified before use, writes are rejected unless the target table belongs to that group, and unclassified SQL fails closed. A write statement requires the active `WriteTx` minted by that same `StoreCore.transaction`; nested, asynchronous, inactive, and foreign-store transactions are rejected. Reads do not need a write token. Core metadata writes use `StoreCore`'s meta methods; schema-migration writes stay in the migration boundary, outside the group repositories.

### Lease names

The exported `LeaseName` union and `LEASE_NAMES` in `@gajae-gateway/home` define the only kernel leases. Each lease is a non-blocking exclusive flock on a permanent file under `$GAJAEWAY_HOME/leases`; the kernel lock, not the diagnostic owner record, decides ownership.

| Lease | Holder / protected resource |
|---|---|
| `gateway` | Gateway daemon process and home runtime. |
| `broker` | Broker host and private broker-agent provisioning. |
| `update` | Update operation and restart-stack supervisor. |
| `memory` | Gateway memory lifecycle and offline memory import. |
| `adapter-discord` | Discord adapter process. |
| `adapter-slack` | Slack adapter process. |
| `adapter-telegram` | Telegram adapter process. |


## Wire protocol and negotiation

Gateway clients exchange newline-delimited JSON frames over a Unix socket (or stdio). A frame has a profile version and a type: `hello`, `negotiated`, `request`, `response`, `event`, or `error`; an encoded frame is capped at 1 MiB.

A client must start with `hello`, listing `supportedVersions` and optionally `requiredCapabilities`. The server chooses the highest mutually supported profile version, currently from `0.1` and `1.0`, and returns its capability list. No common version produces `incompatible_profile_version`; a missing required capability produces `missing_required_capability`. Unknown optional fields are ignored, while required capabilities are explicit compatibility checks. Requests then invoke catalogued verbs and asynchronous events include `chat.message`, `monitor.event`, and `gateway.stopping`.

The SDK treats transport closure, read/write failure, and explicit `close()` as terminal for that client instance. Pending calls reject, later requests fail locally, and `onDisconnect` reports the terminal reason once (including to late subscribers). Negotiation uses the request timeout; a socket connection/negotiation can be cancelled with `signal`. Recovery requires a new client, not reuse of a dead transport. A failed request may already have reached the server: disconnect is not evidence that its operation did not execute.

The admin process owns reconnect policy separately from the SDK: after a previously established connection drops, it allows one connection attempt or retry timer at a time, uses jittered exponential backoff starting at 500 ms and capped at 30 seconds, and restores event subscriptions on a fresh client. Backoff resets only after 30 seconds of continuous attachment; this bounded stability window prevents brief crash-loop connections from returning retries to 500 ms forever. Disconnect or shutdown cancels the stability timer, and a stale timer callback cannot reset a later connection's backoff. Startup logs attempts while waiting for the first connection; established connections log disconnect and recovery transitions, not every retry attempt. Requests fail while disconnected and are never replayed. Initial startup uses this same retry policy and waits for the gateway to become available. Shutdown cancels scheduled reconnect retries and in-progress reconnect negotiation. The console promptly shows a gateway-disconnected state rather than presenting stale data as live, and recovery refreshes its snapshot. Last-seen turn evidence remains visible across a transport interruption and ages to stalled; no turn history is replayed. Reconnection restores future events, not a history replay. This does not change adapter-specific reconnect policy or manage the gateway service.

## Conversation identity and sessions

An origin is a validated, platform-neutral record: platform, kind, conversation ID, and (only where appropriate) parent or peer IDs. Platforms are `loopback`, `discord`, `telegram`, `slack`, and `monitor`; kinds include DM, channel, thread, topic, loopback, and monitor event type. `discord`, `telegram`, and `slack` are the *chat platforms* (`CHAT_PLATFORMS`): the only origins the message and reaction verbs accept, because only they have an adapter that can settle a delivery. Slack thread origins carry a `channel:ts` conversation id with the channel as parent; Slack has no `topic` kind. Discord thread origins may also carry `threadVisibility` (`public` or `private`) as delivery-safety metadata; it is excluded from `originKey`. A missing or unarchiveable Discord thread falls back to its parent only when visibility is explicitly public, never for private or unknown threads. The only canonical identity string is `originKey`:

```text
platform/kind/conversationId[/parent=…][/peer=…]
```

It is opaque after creation—callers must not parse it back into fields. Each origin key has one persistent broker-hosted `gjc` session and an epoch. `/new` (and `/reset`) increments that origin’s epoch and binds the next turn to a new session, leaving other origins untouched. Session creation is idempotent and includes the gateway instance, normalized origin key, and epoch, so a crash around creation can safely retry while the broker remains live.

Inbound messages enter a durable per-origin mailbox actor that applies one rule: if a turn is running, the message is steered into it (`turn.steer`); if the origin is idle, the message is sent as the next turn, immediately. There is no settle window, no coalescing and no age-based expiry: an unanswered row stays `pending` until a turn takes it. Each turn binds its trigger row with a deterministic caller operation reference, the SDK session and a `dispatched_at` stamp before the send; an accepted receipt advances the turn independently of terminal completion. A steer failure never authorizes session replacement or discards the message. An authoritative refusal leaves the row pending until the current turn ends, then sends it as the next turn on the same session; if the turn has already ended, it is eligible for that next send immediately. Ambiguous receipts or transport failures retain the original `clientRef` for observation and same-reference reconciliation, never a new send or a new reference. Session replacement requires explicit operator `/new` (or `/reset`) or a separate, narrowly proven irrecoverable session condition; failed steering is never evidence of that condition and never creates a new epoch or retires the current turn. Session binding happens before any prompt is attached to the row; if a bind epoch's session-create key becomes `terminal_uncertain`, three consecutive bind failures rotate the epoch automatically, preserving every pending row and deriving a fresh idempotency key instead of leaving the channel permanently dead. Model selection also happens before send: a `model.set` failure releases the bound row back to plain pending rather than creating an ambiguous hold; an unavailable session rotates the epoch immediately, while other model failures retry with capped backoff. After send, a `bound` operation whose status remains `unknown` is held once; if the session is positively dead or is live with an empty prompt queue on the second sweep, it is safely requeued on a fresh epoch. An `accepted` operation is never released by that heuristic because it may already have produced side effects. The actor serializes admission, steering, tail frames, broker-generation changes, `/model` live controls, and `/new` fencing. A message the user edits after ingestion is not a new message: the adapter forwards it as `chat.edit` and the gateway streams it into the same session as `[MESSAGE POINTER: <messageId>] …` with the new body - steered into the running turn or sent as the next one by the same rule - while the context ledger's copy of the original is rewritten to the new body. An edit of a message the gateway never ingested is ignored, and the same edit event delivered twice is one update. The adapter keeps an edit that could not reach the gateway (link down, request failed) in a bounded outbox and replays it on the next connect, because message-history recovery cannot reconstruct an edit of an id it already knows. Each bound session has one resident `gjc sdk serve --stdio` relay that is the turn's whole transport: `turn.prompt`, `turn.steer` and `turn.result` go down its stdin as SDK control/query frames, and because the prompt was submitted on that connection the host streams the turn's own content back up it - `agent_start`, every assistant `message_end` (mid-work speech, delivered to the channel as it arrives), `tool_execution_*` (presence), and `agent_end` - stamped with the turn's `commandId`/`turnId`. Frames with another correlation are dropped; nothing is polled, paged, cursored or de-duplicated by text. A relay that dies mid-turn loses that turn's remaining content (host content is best-effort by contract); the turn then settles from `turn.result` status and its original-result body, and the handle reopens for commands. `session status` remains terminal authority. Different origins work concurrently, but same-origin persona, worker, and monitor requests use the shared `SessionPort` lock. A terminal failure generates a visible, ledgered notice carrying the runtime's own error code and message, truncated but never erased, with only secrets redacted:

```text
[turn failed] spawn_failed: SDK startup did not complete before readiness cutoff. Send /new to rebind this conversation.
```

That string goes to the daemon log. The room gets the same diagnosis behind a line a person can act on, so a channel transcript is still enough to triage without shell access:

```text
[turn failed] This message was not answered. Send /new to start a fresh conversation, then send it again.
(diagnosis: spawn_failed: SDK startup did not complete before readiness cutoff.)
```

The `/new` remedy appears only when a rebind is plausibly the remedy; otherwise the room is asked to resend. The `terminal_failure` log line also carries the SDK `command=`/`turn=` ids, the only key that joins a redacted `internal: Prompt submission failed.` to gajae-code's local `SDK invocation failed` record holding the real cause.

`/model` applies `model.set` to the existing session through that mailbox; it neither changes the epoch nor truncates the transcript, and each subsequent persona turn logs its effective model. `/new` is the explicit recovery boundary: it atomically advances the epoch, fences stale output, and discards only pending messages not yet in a turn - the one path that completes an inbound row without answering it. Accepted prior-epoch turns retain their bound session identity as durable recovery holds, so a restarted actor can reattach status/tail until terminal reconciliation; the gateway never invents a replacement operation reference or aborts a running SDK turn.

An authenticated structured `turn.prompt` refusal with exact code `model_not_selected` proves the prompt was not admitted. Before awaiting tail closure, notice delivery, or other fallible cleanup, the gateway transactionally calls `retryInboundTurn` to return the trigger to plain pending and pauses that origin in memory, preserving the current session and epoch without adding a durable hold. It emits one ledgered `[turn failed] model_not_selected: … Send /model <id> or /new` notice per message, with a stable diagnostic delivery ID distinct from the eventual answer. Normal delivery retry and retention rules still apply; the notice does not consume the trigger's answer slot. Dispatch attempts blocked by the pause emit one `reason=model_not_selected` diagnostic containing identifiers only, never message content; no pause diagnostic is emitted when there is no pending dispatch. A successful mailbox-serialized `/model` clears the pause and lets the pending message run on the same session; a failed selection leaves it paused. The refusal's `retryInboundTurn` also advances the durable per-trigger retry ordinal shared with the one automatic submission-phase re-send, so this intentionally conservative sharing spends that budget: the resumed, accepted turn's own submission-phase failure is settled once through the ordinary failure path with no re-send; no op-ref sequencing reset, separate retry counter, or hold is introduced. Restart clears the in-memory pause. `/new` (or `/reset`) discards the pending message under the existing reset rules and allows fresh input. Diagnostic text containing that code, nested detail fields, malformed envelopes, and transport failures do not establish this refusal: uncertain operations retain their existing observe/reconcile behavior and are never re-sent on this basis.

Recognized provider-input/context failures also have a bounded **reset-next** path. Exact current-session provider evidence, rather than occupancy or generic failure text, authorizes one durable consecutive reset per origin. The failed trigger is completed without replay, and subsequent pending messages bind under the fresh epoch without changing the context floor or discarding queued traffic. Reset uses the existing native SDK session operations through `SessionPort`, restricted to positively owned gateway bindings under the current authority; it does not manage broker lifecycle or resubmit old accepted work. Per-trigger deduplication and the origin budget survive restart; an already-retired turn cannot rotate a newer session. Without complete execution-safety attestation from the runtime, the gateway never retries the failed operation merely because it reset the binding.

### Persistent-session observability

A locally bound turn may already have been admitted when its acknowledgement was lost. Canonical `unknown` status, an empty pending-message queue, stale registry idle activity, endpoint absence and timestamp-selected transcript text do not prove non-admission or execution end, across live reconciliation or restart. The actor retains the original operation/session/epoch rather than replaying the trigger or manufacturing a terminal receipt. Authoritative non-admission, correlated native terminal evidence and the separately guarded stalled-turn cancellation path remain distinct supported recovery boundaries.

Guarded stall cutoff requires a positively confirmed `terminated` or `already_gone` host result. Before any awaited cleanup, the actor durably records that confirmation against the exact operation, origin, session, epoch, repository and current broker authority/owned binding. Restart can recover this proof without depending on registry liveness or resuming the dead host. The original native terminal result still takes precedence; otherwise the existing deterministic failure receipt is persisted before turn completion, applicable current-epoch rotation and proof consumption commit atomically. Invalid, foreign, quarantined or unconfirmed evidence never authorizes settlement. A crash before confirmation is durably recorded still leaves the uncertain operation held.

An exact native submission failure can still authorize the existing bounded retry. Successful requeue consumes matching exit proof atomically with releasing the original operation's ownership; it does not broaden retry eligibility. Rollback, a zero-change requeue, or invalid/foreign proof preserves that evidence.

The request helper used for monitor authoring applies the shared canonical operation-state projection before returning an answer. Native `terminal_ok` is accounting completion, not authoring success: cancellation, incomplete stop reasons, unreadable outcomes and missing/unknown receipts raise a status-stage `SessionTerminalError` carrying the original report, without reading a previous assistant response. Local `OpRefError` validation or prompt-fingerprint rejection remains a send-stage error; it never reconciles an older operation as the rejected prompt's result. Genuine lost-acknowledgement and native conflict recovery still observes the original operation reference without replay.

The daemon writes grep-stable fields for the persistent-session control plane: `steer_delivered originKey=… opRef=… messageId=…`, `steer_failed origin=… message=… action=recover` (reconcile the current turn and defer the refused row, never replace the session), `steer_ambiguous … action=replay` and `steer_hold … reason=transport_torn` (observe and reconcile the original `clientRef`, never submit a new send), `tail_frame_foreign session=… commandId=… turnId=… expected=…` (a frame on the relay that belongs to another turn, dropped), `tail_relay_lost session=… opRef=…` and `recovery_hold … reason=relay_lost_mid_turn` (the owned relay died; the turn settles by status), `stall_alert originKey=… sessionId=… silentMs=…`, `compaction_event sessionId=… originKey=…`, and `retired_hold originKey=… epoch=… opRef=…`. A stall alert alone is an operator alarm, not proof of execution end; the separate guarded cutoff must confirm host exit before settlement. Broker-generation changes represent observed changes in the broker service, not gateway-owned daemon replacement. Historical `session_rebound_after_steer_failure` logs identify removed unsafe behavior, not the current recovery policy. A compaction event is observed from a tail frame or authenticated control receipt, never initiated as persona-turn orchestration.

### Worker lanes

An active synchronous `work.run` call owns its exact invocation output before relay attachment and prompt submission, independently of when its completion waiter is registered. A terminal result arriving before the send acknowledgement therefore retains the full proven body, including silent output, rather than only the bounded durable excerpt. Abort, disconnect, shutdown and call completion release this transient response ownership; none aborts or replays the native operation. Recovered attempts without an interested original caller do not retain full response bodies in memory.

Worker `lastActivityAt` (`work jobs` `last=`) is a persisted gateway activity checkpoint: attempt preparation and settlement write their timestamps even without content, and observed real content on the currently bound session can advance it. It is not the SDK's execution/terminal timestamp, proof of observed content, or proof that an operation owns that content or has completed. Work relays negotiate `turn_stream` and `session_host_observer_v1` in addition to `tool_activity_v2`. The SDK sends correlated content to the original submitting connection and uncorrelated observer copies to eligible other connections. Reopening a relay does not transfer invocation ownership: later observer content advances session activity through a separate ingress callback, never through turn correlation adoption, answer delivery, or terminal reconciliation. Content-driven writes are throttled to one per second and fenced by the current open attempt and session binding/epoch; preparation/settlement writes are fenced by the session binding/epoch. Hello, provider heartbeats, status polls, unknown frames, and uncorrelated lifecycle/idle broadcasts do not themselves count as content activity. Content emitted during a transport gap is not replayed; silence is not proof of execution failure and never authorizes retiring live work.

`work.start` binds a gateway-created `work/task/<name>` origin hosted by the GJC broker service in the coding register and returns after acceptance proof, without waiting for completion. An accepted receipt is not a completed task. Its optional `model` is a model ID or `{ "preset": "name" }`; the selection is applied at `session.create` and re-applied on each send. Admission is capped by `work.maxLanes` (default 8). A new name at capacity fails with `lane_capacity` carrying `{maxLanes, active, candidates[]}`, with candidates sorted idlest first; an already-bound name is always admitted by the capacity check.
Each start/wake send prepends a lane notice to the first accepted send in a session epoch, and repeats it if the parent or nested-work policy changes; the notice identifies the parent-report path and forbids direct chat posting. Runs carry no lane notice.

An authenticated `busy` refusal proves only that this prompt was not admitted; the host may still be running other work. The operation journal retains that completed control response and its original prompt fingerprint across retry waits, attachment/model preflight and restarts. Only an exact same-reference, same-fingerprint retry may atomically re-arm it immediately before submission. The next request is durably pending before outbound control; lost acknowledgements and ordinary `unknown` status never authorize another send. Unfinished refusal evidence is not age-pruned. Work-lane recovery reads that local evidence under the session mutation lock and ends only a provably unaccepted attempt through the existing local `send_rejected` path, without inventing an SDK terminal, stopping the host or replaying lost prompt text. Missing evidence, binding/generation revocation and existing acceptance proof remain fail-closed; subsequent work requires the normal explicit start/resume contract.

After the exact owning work attempt is durably settled, its busy-refusal row becomes eligible for the journal's normal completed-operation age cutoff. Transactional pruning requires matching current broker authority, session, operation reference, scope, origin, epoch and repository ownership, and preserves quarantined work. A merely staged terminal, missing owner or unresolved retry never permits pruning; rollback retains the proof.

Overlapping status and prompt-acknowledgement completions return the first durable accepted receipt for the same session, operation and request fingerprint. Native command/turn identifiers are optional: only a conflicting identifier present in both receipts rejects completion. Later observations neither enrich nor overwrite the canonical receipt, and omission never authorizes a resend.

Persona requeue/completion and fenced monitor authoring-pointer abandonment release their exact completed busy refusal in the same transaction as the owner transition. Current broker ownership must still match. A bound/accepted inbound owner or monitor pointer for the operation, monitor metadata with invalid JSON or missing/nontext `opRef`/`sessionId` fields, or a WorkLane runtime for the operation prevents release. Pending/lost-acknowledgement and accepted operation records are never released by this path. Live persona holds and monitor retries retain proof until the durable owner actually relinquishes that operation; age or missing WorkLane ownership alone is not abandonment evidence.

`work.status` is a read-only durable snapshot plus a live query of the matching operation, not an atomic distributed snapshot; it never binds, attaches, refreshes activity, settles an attempt, or acknowledges a hold. Job state, attempt end state, and broker operation status remain distinct. `work.steer` targets only the current open attempt without rebinding; an ambiguous steer reports `work steer acceptance uncertain` and must not be automatically retried with a new reference. An open attempt blocks another start/run, including `resume:true`, and retirement. Synchronous `work.run` uses the same lifecycle but waits only for a response and never reports to a parent. Start and run from a lane session are refused unless `work.allowNested=true`. Caller timeout, disconnect, or gateway shutdown detaches the waiter without settling or aborting the worker. A timed-out run reports `work wait timed out; attempt remains observable`.

The durable observer recovers the original operation/session identity on startup and broker-generation changes, without resend, bind, or replacement. A live matching operation reported as `unknown` is neither acceptance nor terminal proof: keep observing without overlap. A torn send without acceptance proof reports `work send acceptance uncertain`, not a successful receipt. Trusted terminal evidence can finish reconciliation without live reattachment. Without that evidence, unrecoverable dead/disowned/indeterminate recovery authority yields a fail-closed `terminal_uncertain` operator hold; a local end timestamp does not prove the worker stopped. Transient transport loss is not a worker deadline, and repository progress does not clear a sticky uncertainty/failure hold.

Observer authority is revalidated after attachment readiness before submission and after transport-cause diagnostics before settlement or report admission; shutdown, broker-generation changes and binding rotation revoke stale observers even when the durable attempt version is unchanged. Dropping an observer also disposes its resident relay, and pending attachments remain cleanup-owned until they resolve. Shutdown and generation recovery drain tracked disposal, including handles removed from the observer registry. Relay-close failures are logged and contained; teardown never terminates the native host or invents attempt completion.

Observer disposal cancels its pending relay attachment, including capacity waits before a handle exists. Cancellation removes the waiter and releases only that attachment's reservation or acquired relay, including acquisition/readiness races; it never cancels a native turn or closes another session's running relay. Shutdown therefore does not need persona-owned capacity to be released before work-observer disposal can finish.

Revocation before the initial `send` call checkpoints a local `send_rejected` outcome with the latest attempt-version CAS, unless acceptance or terminal evidence already exists. This records positive knowledge that submission never happened, not an SDK terminal or proof that the host stopped. Recovery settles that rejected attempt without replay and permits a subsequent explicit resume. Revocation after submission may have started remains acceptance-uncertain and observe-only.

Both work verbs accept `callerSessionId`, forwarded by the CLI from `GJC_SESSION_ID`. It is an untrusted routing hint on the owner-trusted socket: socket clients are owner-equivalent, so the nested-lane gate is policy, not a security boundary. Start parent resolution prefers a recognized persona caller, then a permitted lane caller. A caller in one monitor's event session reports to that monitor's chat `channelTarget.origin` conversation. If none applies it falls back to `ownerTarget`, and otherwise has no parent; a monitor caller whose target is missing, deleted, malformed, or not a chat origin takes that fallback with `fallback=monitor_<reason>` on its `work_parent_resolved` log line.

Lane report text uses `[lane <name>] completed|failed|attempt_ended: …` with bounded classified content, never raw SDK exceptions. SDK failure cause takes precedence over missing-receipt diagnosis: deadlines retain `prompt_deadline_exceeded` and their `attempt_ended` disposition, classified provider transport failures retain `provider_transport`, and other SDK failures retain `sdk_failed`. Receipt state remains an independent stored/reported dimension. Allowlisted outcome code, provider code, phase, category and provenance survive the authenticated status boundary and strict durable validator; raw messages and arbitrary diagnostics do not. Only an otherwise unclassified terminal uses `terminal_missing_receipt`. Cancellation and incomplete outcomes are not success. Completed work whose answer cannot be proven says `completed: output_unavailable`; synchronous `work.run` remains response-only and reports `work output unavailable` without rewriting known broker completion.

A failed SDK status without a present receipt, or a `terminal_ok` status explicitly carrying `receiptState=missing`, needs independent execution-end proof: its matching `agent_end`/`agent_failed` lifecycle frame, or a live `context.get` snapshot reporting `isStreaming=false` and both turn queues empty, followed by unchanged correlated terminal status for a started operation. Execution frames during the probes invalidate idle proof. The observation persists across recovery. A request deadline, transcript final, broker activity label, unknown operation status, incomplete snapshot or unavailable probe is not execution-end proof; without proof the attempt stays open. Legacy `terminal_ok` handling for unknown/absent/omitted receipt state is unchanged; those states are not new success evidence. After execution end, bounded output reads allow the SDK to attach a final body late. For a failed nonpresent receipt (including unknown/absent/omitted state), or the existing missing-receipt case, only a proven complete original same-operation body can upgrade the receipt using its actual correlated outcome; `end_turn` settles `completed`, while an unknown outcome remains `stopped_incomplete`. The original observation and native operation identities must match; settled reports remain immutable. Missing output neither proves nor disproves repository changes.

Fresh-session recovery is not implicit in `resume:true`: ordinary binding may reuse the live predecessor. The pinned SDK's create/fork APIs do not establish identity-fenced exclusive transfer of its existing worktree, and `session.checkpoint` is a transcript cursor rather than a writer-exclusion token. A same-worktree successor remains blocked until authenticated exclusive admission can exclude predecessor/owned-job writes. Explicit isolated new-name/new-worktree continuation is a separate task with reviewed evidence, source/successor linkage, preserved owner and fresh instructions, not replay or proof the original stopped. Attempt history, uncertainty and original worktree/files must be retained. SDK `activity.at` records state transitions, not a progress heartbeat; neither age nor transcript final text authorizes host termination.

A settled start result is reported to its selected parent as an internal lane report turn, not as a human message. Persona parents receive an internal inbound row; lane parents use the durable lane-report inbox, which steers an open parent attempt or wakes a new one when `work.allowNested` is enabled. Reports follow the formal lane -> persona -> human path. A run is response-only and never reports.

Idle reconciliation requires a ready, operation-correlated activity observer throughout both probes. A CLI idle snapshot during attachment or reconnection is not end proof. Synchronous correlated ingress, relay loss, and connection-incarnation changes invalidate the observation. A native `agent_start` also invalidates pending idle/death proof even when uncorrelated and before any content arrives; this does not attribute output or advance the content activity checkpoint. An uncorrelated end still cannot prove attempt completion. A permanently dead activity observer is readopted without resending or restarting its work.

A missing-receipt attempt whose runtime cannot answer can independently prove execution end when broker inspect positively reports `live=false` (not disowned) throughout the 30-second host-lost grace, followed by unchanged correlated terminal status. An observed SDK failure retains its causal terminal; otherwise the existing `session_dead` fallback applies. Streaming or queued execution blocks this fallback. Execution frames, unknown/disowned/failed inspect probes, and observer restart break the grace and cannot alone settle a lane. This covers a cached request failure that outlives a host without lifecycle delivery; it does not infer success, create a receipt, or replay work.

Recovery also refreshes an already-saved failed terminal without a present receipt, or a terminal explicitly carrying a missing receipt, when execution-end observation is absent; saving an SDK failure does not make it execution authority. The same correlated idle/death proofs gate retrieval, while a refreshed matching terminal receipt can release it directly. Saved terminal evidence remains unchanged until proven output reconciles a late receipt: confirmed death releases the bounded output budget but retains the observed failure cause and receipt dimension. The router-unavailable status/inspect path is also fenced to one activity version: native starts and observed activity reset both host-loss grace accumulators, and evidence interrupted during either probe cannot seed a new grace window. Restart, observer replacement, and broker-generation recovery neither resend work nor create another settled report. Restart-interruption/drain guarantees and the SDK busy-state root cause are separate from causal classification; this path does not establish that in-flight work survives a restart.

Lane-report origin resolution leaves admitted Discord channel and thread origins unchanged, including any supplied thread-visibility metadata. A channel trigger message ID is not evidence that a Discord thread exists. Only Slack channel roots are resolved to trigger-message threads, using Slack's `channel:ts` message identity.

A run gjc starts on its own (for example the wake that hands a persona an async `task` or async `bash` result after its turn ended) has no SDK submitter, so its content never reaches the gateway. The gateway therefore retains each settled persona turn's relay as a lifecycle-only observer (2-minute grace, extended while jobs run, activity is non-idle, a runtime-started run is open, or a probe is unavailable; 6-hour cap). When a runtime-started run (opened by an uncorrelated `agent_start`) ends and no jobs remain, the gateway enqueues one internal notice row (`agent-run/<sessionId>/<batch>`, source `lane_report`, coalesced while undispatched) that asks the persona to resend anything undelivered or answer `[SILENT]`; the resulting gateway-owned turn uses the ordinary delivery ledger. This is best-effort recovery, not verbatim replay: it costs one extra model turn, and a run that both starts and ends while the gateway is down with no jobs left is not reconstructed. Observer-only reverse requests (permission/UI) are answered unavailable, as when no relay was open.

If parent admission fails, the report uses exactly one fallback delivery-ledger row; the physical post is at-least-once, so a crash after posting may produce a duplicate. A parentless result is durably `no_target`. Pending, claimed, held, and undeliverable lane reports are visible through `work jobs`; its `reports=p:N c:N h:N u:N` counts are printed when any count is non-zero. Ambiguous delivery remains held, and a report with no root fallback is marked undeliverable.


Worker output requires proven attempt-final attribution and complete original content: a timestamp alone, a neighboring prior reply, intermediate tail text, completed pagination, or a summary is not proof. The exact pre-send floor has no two-second tolerance. Intentional silence is recognized from the proven original final body before prefixing or truncation, persisted before dependent tail checkpoints, and suppresses lane reports even if later text is unavailable or authority uncertain. Missing provenance means unavailable output, not assumed silence. Post-terminal output acquisition has three durable reads across restarts (immediately, then after 1 second and 5 seconds); invalid attribution or definitive unavailability ends retrieval early. This finite retrieval budget starts after terminal proof and never limits worker duration.

`work.retire` closes only a positively owned, gateway-created gjc session with `session.close` and bumps the origin epoch, so the next start/run creates a fresh session. Retirement is fail-closed on ownership: it refuses while the lane job has an open attempt, while the job record is corrupt, and while the last attempt ended without trusted broker proof until the operation is proven terminal or the broker reports the session dead. In particular, `terminal_uncertain` is not proof of stoppage. A failed `session.close` releases the slot only when broker liveness proves the session gone; otherwise the binding is retained and the refusal names the close error, because an uncounted live worker is the exact failure the governor exists to prevent. The 60-second sweep nominates lanes idle for at least `work.idleRetireMs` (default 6 hours, measured from the last attempt's end) or whose lane job is `done` or `aborted`, and each nomination is re-proven under the lane lock against the session id it was selected with, so a lane reused or rebound meanwhile is left alone. The gateway never performs global GC or `session.delete`; retirement bounds owned live worker hosts, not the user's saved-session index.

`ops.cycle` reports `lanes: {active, max}` and gates on `lane_capacity_exhausted` when the cap is reached. A retired lane keeps its `work/task/<name>` row unbound; that row is healthy only while a settled lane job (`attempt_ended`, `done`, `aborted`) vouches for it. The same unbound shape with no job (a failed first bind) or with a `running`/`awaiting_operator`/`stalled` job (a crash-left or held worker) stays a `stale_session_identity` gate. An origin unbound by a broker-authority cutover is quarantined history, not a rebind in progress, while nothing has addressed it since: no inbound row, lane job or monitor event for it outside quarantine, and no `last_activity_at` past the cutover. Once any of those exists (for example an inbound turn whose first bind fails, which leaves the session row untouched), it is gated again until it binds. The ActionGuard system notice recommends start/status/steer for delegated long work and forbids direct `gjc` launches from persona turns as prompt guidance, not a new command-enforcement hook. Workers share the user's broker but remain separately owned gateway sessions; unrelated user sessions are never adopted. Host skill/script replacement, deployment, and process cleanup are separate operational work, not part of the worker-lane API change.

Force-retiring a lane whose completed attempt is still awaiting checks concludes that checks cycle and admits its ended-outcome report in the same transaction, using the recorded PR/head without inventing fresh check results. The original attempt's terminal, output, settlement and report identity remain unchanged. The conclusion has a distinct logical receipt identity and follows existing persona, nested-lane or fallback routing; repeated retirement, recovery and late checks polls cannot conclude the cleared cycle again. Proven silence and response-only/no-target work remain unreported, including normal checks conclusions. Physical delivery remains at-least-once.

Worker-lane logs are grep-stable:

- `lane_retired name=… session=… reason=operator|idle|job_done|job_aborted closed=…`
- `lane_close_failed name=… session=… detail=… action=retained|session_gone`

The persona preamble comes from `SOUL.md`, `AGENTS.md`, and `USER.md` in `$GAJAEWAY_HOME/workspace`; the same directory is passed to `gjc` as the session working directory. It is not resent on every turn: the persona actor puts it into a session's context on the first send, when its text changes, after a failed turn, when the context usage read from `context.get` on the turn's relay is lower than at the previous send (compaction or pruning removed history) or unreadable, and every 25 sends as a bound for a compaction the usage samples cannot see. Every other send relies on the copy already in the context. Each injection logs `persona_preamble origin=… session=… reason=first|changed|compacted|usage_unknown|context_shrank|refresh context_percent=…`.

Before each persona send the actor also keeps the session clear of gjc's own compaction line (300K tokens by default). gjc compacts a session that a prompt would push over that line before accepting the prompt, inside a 30-second wait it cannot meet at that size, so the prompt fails. When `context.get` reports 200K tokens or more, the actor runs `compaction.run` first, before the turn starts and with the origin's queue held, so no steer or later send reaches the session mid-compaction; the send that follows carries the persona preamble again (`reason=compacted`). Each run logs `persona_compaction origin=… session=… opRef=… tokens=… status=succeeded|failed|skipped|unavailable elapsedMs=…`. A compaction that does not succeed does not block the send.

The first attempted turn in every origin epoch also receives a trusted `Session bootstrap` system section. Its stable ID is derived from the opaque origin key and epoch. It carries current conversation metadata plus bounded navigation from `$GAJAEWAY_HOME/memory`; it is never placed in unread/user text. The serialized section is capped at 8 KiB by UTF-8 bytes. Identity is mandatory, today and yesterday receive bounded priority shares, and recoverable channel/rules/navigation pointers consume only the remainder. Daily sources alone may be labelled newest-entry excerpts and have a 4 MiB read ceiling; other sections remain whole. Excerpts, read-ceiling drops, and budget omissions all set truncation and are named explicitly. Source paths are realpath-confined to…

Bootstrap completion is durable in schema 14. An epoch is pending while `epoch > last_bootstrapped_epoch`; `/new` establishes pending state in the same session-row update that bumps the epoch. The gateway commits the projection only after a terminal text or intentional-silence success. A failure before terminal success retries with the same stable bootstrap ID. If an intermediate reply was already delivered before failure, the unread body is consumed to prevent a harmful answer replay, while the still-pending bootstrap is safely re-presented under that same idempotent ID on the next turn. Session and ops projections expose only epoch, applied time, included section names, byte count, truncation, and diagnostics—never source bodies.

## Cross-session handoff, post, wake, and watch

`[HANDOFF:<target>] note [HANDOFFDONE]` moves work to another chat origin; `[POST:<target>] text [POSTDONE]` (also spelled `[SEND:…] … [SENDDONE]`, or a part opening with `[REPLY:<channel>]`) posts the text itself into another configured channel of the same platform. Routing blocks may sit anywhere in a reply and one reply may carry several; text outside them is delivered in the source conversation, tokens quoted in code are text, any close token ends an open block, and an unclosed block ends at the next opener (a post also at the next `[BREAK]`) or the end of the reply. Handoffs to one target are merged into one hop, and posts are sent once, from the final answer. A post target may be spelled as a canonical origin key, a `handoffTargets` alias, `<platform>:<channel id>`, `<#channel id>` or a bare channel id. `[WAKE:<target>] <summary>` sends an explicit information-only relay while keeping the work here. A final reply may also register a one-shot `[WATCH:<target>] <ttl> <reason>` for the next accepted human message at another origin. Watches are durable in schema 34, unique per waiting/watched origin pair, expire between one minute and seven days, and are claimed atomically with the source message's durable inbox admission. The resulting internal turn carries sender, origin, and queue status only; it never copies message text, attachments, secrets, or the free-text watch reason. The reason stays in the durable watch record and is omitted from shared daily-memory events. Provenance uses the same two-hop and loop checks as relays, and the wake grants no authorization. Watch registration and firing are recorded as origin-tagged daily-memory events.

## Delivery and crash semantics

Before an outbound reply is emitted, the gateway creates a durable ledger item. States are `pending`, `inflight`, `confirmed`, `failed_ambiguous`, and `expired`. Adapters mark an item inflight before attempting platform delivery and confirm it after success. A non-ambiguous failure returns to `pending` with exponential backoff (2 seconds, doubling to a 5-minute cap); the fifth definitive failure expires it. An ambiguous failure stays `failed_ambiguous` regardless of its failure count. Any unsettled item older than the 24-hour freshness window expires during a delivery sweep.

At negotiated connection time and every 15 seconds while an adapter is connected, adapters receive due unsettled deliveries. This is deliberately at-least-once delivery: an `inflight` or `failed_ambiguous` item is reissued with `redelivered: true` and `duplicateWarning: true`. Platform adapters must display the duplicate warning. Confirmed or expired records are not replayed automatically; expired counts and the five most recent identifiers/origins are exposed by `gateway.status`, and the admin console raises attention. Expiry is logged and an owner-target notice is sent once per delivery when configured. Operators can requeue eligible rows with `gajaeway ops redeliver <deliveryId>` or `gajaeway ops redeliver --since <iso>` (selecting rows updated since that timestamp). Confirmed records are never requeued; old confirmed records are pruned after seven days.

Broker mutations are journaled in `broker_operations`, intent first. `session.create`, `turn.prompt`, and `session.close` each write a `pending` row in its own transaction before the broker call, carrying the broker-side reference (`--idempotency-key`, or the prompt's `clientRef`) and the exact request. A crash or broker restart between the call and its completion leaves that row, and the retry replays the same reference: the broker dedups a create or close under its key, and a pending prompt is reconciled with `turn.result` for its `clientRef` before anything is resent, because `turn.prompt` itself is not idempotent. A completed prompt or close returns its stored result without calling the broker. Create keys are fresh per attempt (`gw-bind-<uuid>`), and the intent is released in the same transaction that records the binding, so a later bind of the same origin, epoch and repository never inherits a finished create. A prompt's journaled request is a hash of its text, system preamble, and model, so an op ref reused for a different turn is refused rather than answered from the journal. Completed rows are pruned after an hour and abandoned prompt and close intents after a day; a pending create is never age-pruned, because only its original key can recover a session the broker may already have made. A `work.start` issued while the supervisor restarts the broker waits for it (`waitForBroker`, the same bounded backoff boot uses, capped at two minutes) instead of failing `work lane bind failed`; only an unavailable broker is waited on. That includes a lane reusing its persisted session: an unavailable broker during the bind's `session inspect` (or a resume it triggers) is surfaced to the wait instead of reusing the session unchecked.

### Functional readiness

`gateway.status` reports process liveness separately from functional readiness. Readiness degrades after three consecutive failures in the same category (`session_create`, `turn`, `delivery`, or `monitor_delivery`) within a rolling five-minute window. A successful operation in that category clears its failure streak; old evidence expires. The payload includes a bounded failure code, sanitized detail, timestamp, and origin; `gajaeway status` prints the payload as JSON.

## Engagement and safety floors

Loopback is trusted locally, while DMs use `dmPolicy`. Group traffic uses one gateway-owned channel policy: `engagement` is exactly `open`, `mention-open`, or `closed`, and `audience` is independently `all`, `human-only`, or `bot-only`. `open` admits matching-audience chatter; `mention-open` requires a real mention or native reply to this bot; `closed` ignores audience and requires both addressing and the existing owner/allowlist authorization. Omitted engagement remains closed. Omitted audience remains `human-only`, preserving historical `engagement: "open"` behavior: humans are open while bots fall back to the closed gate. Discord threads inherit a configured parent channel policy unless the thread has its own entry.

Discord drops self-authored messages before forwarding and the gateway durably deduplicates platform message IDs. Bot turns admitted through an explicitly widened audience have no consecutive-turn cap by default: `audience: "all"` means bot messages are turns, so several agents can collaborate in one thread. Two budgets bound them. `botAudience.maxConsecutiveTurns` (global) and `channels.<key>.botAudienceMaxConsecutiveTurns` cap consecutive bot turns per conversation when set, and a human message resets that count. An always-on rolling-minute rate limit (`botAudience.maxTurnsPerWindow`, default 30 admissions per conversation) is what stops a runaway bot-to-bot loop; a human message does not reset it. Rate-limited and budget-spent declines are logged with the origin, its current consecutive and windowed counts, and are projected by `gateway.status` as `engagement.botAudienceDeclines` and `engagement.botAudienceRateLimited`.

The gateway gives `gjc` unoverridable ActionGuard guidance. It forbids unrecoverable commands such as recursive removal of `/`, filesystem formatting, raw device writes, and fork bombs. It also refuses recursive deletion of `$HOME` itself or absolute paths outside `$HOME` and `$GAJAEWAY_HOME`. These are floors, not a configurable permission bypass.

Outbound chat is redacted by the gateway itself (`guard/secret-guard.ts`). Every `chat.message` (text and `voiceText`; reactions excluded) and every `chat.progress` activity label is filtered at the connection writer, after the ledger and on every redelivery, so no persona instruction, workspace file or `config.json` edit can switch it off. Well-known credential formats (Slack `xox*`/`xapp`, Anthropic `sk-ant-`, OpenAI `sk-`, JWTs, GitHub `gh*_`/`github_pat_`, AWS `AKIA`/`ASIA`, PEM private keys, OpenGateway `apik_`, `Bearer` tokens) become `[REDACTED:<kind>]`. Exact values the process can read are indexed in memory as overlapping 16-character windows of the value, its reversal, base64 (every byte alignment, standard and URL-safe) and hex, with whitespace, quotes, commas, `+`, `|` and zero-width characters ignored, so whole values, 16+ character fragments, encodings and split copies are caught. The values come from secret-named environment variables (`*_API_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, ... but not `*_FILE`/`*_PATH`/`*_DIR`/`*_URL`), `$GAJAEWAY_HOME/secrets/`, files and directories listed in `GAJAEWAY_SECRET_GUARD_FILES`, names listed in `GAJAEWAY_SECRET_GUARD_ENV`, and the credentials in the gjc `agent.db`; they are re-read at most every 30 seconds so a refreshed token is covered. A redaction logs `secret_guard_redacted event=<event> kinds=<kind>:<count>,...` and never any part of a value. The persona also receives a gateway-owned system clause that forbids revealing secrets in any form. `gajaeway-gateway redact` applies the same filter to stdin for tools that post to chat without the gateway.
